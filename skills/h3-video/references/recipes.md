# 配方与参数

什么时候读：要决定一段戏用哪套采样配置、要改步数或分辨率、要在别的工具里搭等效工作流，或者要手写 `shots.json` 时。

参数以 `scripts/drama_queue.py` 的实现和作者最终出片用的预设为准（2026-11 定稿；显卡 RTX 5060 Ti 16 GB，ComfyUI 0.45）。自己的工作流怎么接这套配方、哪些节点由脚本加，见 [queue.md](queue.md) 的“接入你自己的工作流”。

## 一张表：文戏和武戏只差 LoRA 和接续

| | 文戏 | 武戏 |
|---|---|---|
| 采样结构 | 专属二采 | 同左 |
| 一采 | 1024×576，10 步，euler | 同左 |
| 放大 | 潜空间 ×1.5，到 1536×864 | 同左 |
| 二采 | beta 调度 14 步，从第 8 步切开，只跑后 6 步，euler | 同左 |
| LoRA | 一个都不挂 | 5 个 LoRA 的链，见 [lora.md](lora.md) |
| 段间接续 | 站位对上就硬切，不接续 | 接上一段末尾 22 帧加音频（`ctx`），拼接时剪掉 |
| 每秒成片耗时 | 约 1.5–2 分钟 | 约 2.4–2.7 分钟 |
| 可信度 | 已验证（多次出片、作者看原片认可） | 已验证 |

耗时是队列记录的墙钟时间，含每段重新加载模型，分辨率 1536×864、24 fps。用时与片长大致成正比：10 秒一段，文戏约 15–20 分钟，武戏约 24–27 分钟。武戏更慢，部分原因是每段多算了 22 帧接续（约 0.9 秒）。

## 两套共用的参数

| 项 | 值 | 为什么 |
|---|---|---|
| 底模 | Cobijada Hybrid（int8，FL 与 REF 权重混合版），`models.unet` | 参考生视频和首帧生视频都能跑；作者几轮对比后看片最好 |
| 文本编码器 | Qwen3-VL 32B int8 的普通版，`models.text_encoder` | 与去限制版看不出差别，见 [uncensor.md](uncensor.md) |
| 一采 sigma | `1, .9882, .973, .9524, .9231, .878, .8, .6316, .4737, .1579, 0`（10 步） | RunningHub 上流传的 10 步曲线；末尾 `.4737 → .1579 → 0` 被认为起精修作用（推断）；来源见 [credits.md](credits.md) |
| SigmaShift | `MiniMaxH3SigmaShift`，视频 12、音频 3，接在 LoRA 之后、采样之前 | 二采的 beta 调度由这个模型算出 |
| 引导 | `BasicGuider`，CFG 1 | 所以负面提示词基本不起作用 |
| 稀疏注意力 | Sol 稀疏注意力，默认开 | 关掉（`dense: true`）在作者的 10 秒开场文戏段（下称 g1）、1280×736 单采上要 25 分钟而不是 17 分钟，看片还更差 |
| 参考图尺寸 | `match` | `max` 在作者的一次对照里只多约 3% 时间，社区报告说会慢很多；没有记录到看片结论，所以保持默认 |
| 帧数 | 取 `17k+5`，10 秒约 243 帧 | 脚本按这个规则向上取整；90、107、175 这类数才合法 |
| 种子 | 一个固定值 | 只有同一提示词抽卡时才换，否则没法归因 |

## 二采到底做了什么（以 `up2` 的实现为准）

1. 一采跑完整条 10 步曲线，得到视频加音频的联合潜变量。
2. 拆出视频潜变量，用潜空间放大模型放大到 `up2.w × up2.h`。节点填的是目标宽高，不是倍数，所以 1024×576 → 1536×864 恰好是 1.5 倍。音频潜变量原样保留，再拼回去。放大模型即 `models.latent_upscaler`（社区的 3D 卷积版，fp16，约 0.64 GB）。
3. 二采的调度：在带 SigmaShift 的模型上用 `BasicScheduler`（beta，14 步）算一条新曲线，在第 8 步切开，只取后半段，也就是 6 步。
4. 采样器 euler。噪声用与一采同一个种子的噪声节点，在放大后的潜空间上按后半段起点的噪声水平重新加噪，再去噪到 0。
5. 如果有首帧、末帧或接续锚点，要在放大后的潜空间上重新加一遍，并为二采单独建一个 guider。

整条链一共采样 10 + 6 = 16 步。

## 自己搭等效工作流时的接线要点

- **二采宽高必须是 32 的倍数。** 1536×864 和 1568×896 可以，1584×912 在二采报 shape 错误（单次实测）。
- **首帧锚点（`MiniMaxH3AddGuide`）是按一采潜空间的尺寸写进条件里的，放大后必须重新加。** 否则二采报 `shape mismatch`。作者的第一段接首帧的片就是这样失败的。
- **音频潜变量要对照一个已知能出声的工作流来接。** 作者在另一条两阶段流程里把音频接反过，画面正常、声音带噪声，三段成片受影响。
- **节点上显示的数字不一定是生效的值。** 作者最初照抄时把放大倍数和一采分辨率抄错：放大节点上的 1.5 是摆设，真正的倍数由一个变量连线传入。要沿连线追到来源。

## shots.json 写法（文戏）

```json
{
  "id": "g2", "take": 300, "seed": 7100, "seconds": 10,
  "prompt": "……", "images": ["角色定妆图.png", "场景图.png"],
  "clip": "<models.text_encoder>",
  "w": 1024, "h": 576,
  "sigmas": "1, .9882, .973, .9524, .9231, .878, .8, .6316, .4737, .1579, 0",
  "sampler": "euler",
  "shift": [12, 3],
  "up2": {"w": 1536, "h": 864, "sched": ["beta", 14], "split": 8, "sampler": "euler"},
  "save_stage1": true
}
```

武戏在此基础上加 `"loras": [[文件名, 强度], ...]`（五个，顺序见 lora.md）和 `"ctx": "@上一段id_t版本号"`。字段含义见 [queue.md](queue.md)。

**一定要把配方字段写进每条 shot。** 没写的字段沿用你导出的工作流里已有的值，那不一定是现在的配方（原版脚本是落到早期的 15 步单采、1280×736）。作者的做法是用一个预设字典合并进每条 shot，换配方只改预设；仓库里这件事由 `scripts/build_shots.py` 做（文戏预设不挂 LoRA，武戏预设挂 `models.fight_loras`，默认值可在 `config.yaml` 的 `recipe:` 里改）。

## 先出一采预览，再统一二采

同一个种子、同一个一采分辨率下，一采和二采的构图、动作、时间几乎一致（2026-11-19 一次观察，单次实测）。所以可以先只跑一采（去掉 `up2`）定下镜头，满意后再用同一个种子出二采。加上 `save_stage1: true` 也会把一采单独存成 `_stage1` 视频，方便对照二采到底改了什么。一采单跑的耗时没有单独记录（未验证）。

## 改参数的代价（g1，10 秒，同提示词同种子）

g1 是作者那部片的开场文戏段：10 秒、一镜到底。各个文件里的 g1 都指它；f1、f2 是片中前两段武戏。

| 改动 | 结果 | 详情 |
|---|---|---|
| 基准：1024×576 → 1536×864 | 906 秒 | |
| 一采改 1056×608 → 1568×896 | 慢约两成，看不出区别 | 作者选回 1536×864 |
| 放大到 1.8 倍 | 一段约 47 分钟 | [tried-and-dropped.md](tried-and-dropped.md) |
| 二采目标设到 1920×1104 | 溢出共享显存，83 分钟 | 同上 |
| 一采换 beta 24 | 1362 秒，更软 | 同上 |

## 可信度

- 已验证：两套配置的结构和参数、`17k+5` 帧数规则、32 的倍数限制、锚点重加。
- 单次实测：各项改动的耗时和画面结论。
- 未验证：12 GB 显存、其他底模、一采单跑的耗时。
