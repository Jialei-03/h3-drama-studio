# 可选：本地文本大模型（Basalt）

什么时候读：除了出视频，还想在同一张显卡上跑本地文本模型（聊天、写提示词、接 agent），或者要调它的速度、排查它启动失败时。不做这件事，整个文件可以跳过，视频配方完全不依赖它。

作者用的是 Basalt 推理引擎（0.3.3）加 Qwen3.8-Flash-Next 的量化包。**下面所有数字的条件是：** Ryzen 5 9600X（6 核）、96 GB DDR5-5600、RTX 5060 Ti 16 GB、Windows 11、上下文 128K、KV 用 int8、投机解码 `spec` 8。换机器或换引擎版本，数字全部要重测。文本服务的地址文中写作 `<text_url>`；它是可选组件，所以 `config.example.yaml` 里没有这一项。

## 显卡和视频不能同时占用

16 GB 不够两边同时放。切换前先卸载另一边：

| 方向 | 做法 |
|---|---|
| 文本 → 视频 | 在引擎的监控页卸载模型，或 `POST <text_url>/v1/unload`，再启动或使用 ComfyUI |
| 视频 → 文本 | 对 ComfyUI 发 `POST /free`，body 为 `{"unload_models": true, "free_memory": true}`，确认 `nvidia-smi` 显存已降，再加载文本模型 |

ComfyUI 出完片不会自己释放显存，约 13 GiB 会一直占着；这时直接加载文本模型，它会因为显存不足把专家缓存缩小，速度变慢。

## 量化包怎么选

| | 3 bit（IQ3_S） | 官方 NVFP4 |
|---|---|---|
| 质量依据 | 官方 IQ3_S 档对 BF16 的 KLD 0.150、top-1 87.56%；社区包本身没有公开评测 | 官方评测 KLD 0.062、top-1 91.65% |
| 速度（对话、散文） | 快 20–30% | 慢一些 |
| 速度（结构化输出、长文读入） | | 持平或略快 |
| 常驻内存副本 | 约 40 GiB，可锁页 | 约 64 GiB，在 0.3.3 上锁不了页 |
| 冷启动 | 约 25–30 秒 | 闲置后首次加载明显更久 |

读长文、调工具、输出 JSON 的 agent 工作选 NVFP4，几乎没有速度代价；聊天和写作为主选 3 bit。同一次会话固定用一个。按体积推算，16 GB 显存加 64 GB 内存的最低配置装不下 NVFP4 的 64 GiB 副本（未验证），见 [hardware.md](hardware.md)。

## 日用参数

| 项 | 值 | 为什么 |
|---|---|---|
| 上下文、KV | 131072，`int8` | 弹性 KV 只预留 32768 格，其余借给专家缓存，128K 对短对话几乎没有代价；官方评测 int8 相对 fp16 无可测质量损失 |
| 投机解码 | `spec` 8 | 实测 8 > 4 > 3 > 0，结构化输出受益最大 |
| 长文读入 | `prefill` 不写（自动） | 固定 512 时 64K 读入约 805 tok/s，自动约 2,200 |
| 并发 | `parallel` 1 | 单卡两路总吞吐不增，官方也建议一路 |
| 常驻预算（仅 3 bit） | `resident-budget-gib` 45 | 见下一节。NVFP4 不要加这个键 |

## Windows 锁页上限

Windows 的显示驱动模型限制一个进程能登记给 CUDA 的锁页内存，作者的机器上约为物理内存的一半：**46.82 GiB**（物理 93.6 GiB）。引擎把不在显存里的专家放进一块内存副本并整块登记；超过上限，登记整体失败，引擎日志写 `page-locking refused (out of memory)`、`pinned 0.00 GiB`。数据还在内存里，但传到显卡变慢。

- 3 bit：128K 加自动分块时副本 47.57 GiB，超线 0.75 GiB。加 `resident-budget-gib 45` 后副本 39.74 GiB，全部锁页，综合速度从 83.6–85.8 提到 88.0–88.7 tok/s（各 3 次冷进程）。
- NVFP4：副本 64.27 GiB，锁不了。设限额 45 也不锁页，还把 10.7 GiB 留在文件映射上，没有收益。
- 检查：加载后在 `engine.log` 里找 `cache complement ready`，确认 `pinned` 等于 `resident`。
- 0.4.0 改了登记失败时的分配方式（上游 #297），可能让 NVFP4 受益；但有已知退化：限额不小于专家补集时解码速度减半（上游 #366）。升级前先看修复是否合并。

## 实测速度

单位 tok/s，每组是一次独立的冷进程，官方 `basalt-bench` 的 conv、struct、prose 三类加 64K 读入，挂着投机解码。

| 配置 | 对话 | 结构化 | 散文 | 综合 | 64K 读入 |
|---|---:|---:|---:|---:|---:|
| 3 bit，不锁页，3 次 | 59.1–62.8 | 94.5–97.7 | 59.5–62.7 | 83.6–85.8 | 2,230 |
| 3 bit + 预算 45，3 次 | 65.6–68.2 | 96.9–98.3 | 65.1–67.8 | 88.0–88.7 | 2,160 |
| NVFP4，热状态，2 次 | 45.7–52.0 | 96.7–102.8 | 54.5–55.7 | 79.3–84.2 | 2,334–2,383 |

首字等待（16K、32K、64K 输入，单位秒）：3 bit 为 9.0、15.5、30.5；NVFP4 为 8.7、13.7、27.7。同卡 Linux 用户报告的 3 bit 综合速度为 137–159，同提交同硬件下 Windows 与 Linux 相差约 29%；官方文档说明 Windows 没有基准。

## 测速时容易得出错误结论的地方

1. **测速对同机负载极敏感。** 专家计算有一部分在 CPU 上，6 核不够富裕。测试期间主机上有下载、校验、拷贝视频，对话速度会从 65 掉到 32 tok/s，16K 读入从 1,900 掉到 650。**测速时不要碰主机，包括通过 SSH 读文件。** 空闲时连续三轮的波动在 3% 以内。
2. **闲置后的第一组偏慢**（权重要重新读入文件缓存，NVFP4 尤其明显）。先跑一组丢弃，或把各配置交替跑几遍。作者曾把它误记成"原因未明的性能下降"。
3. **不同时段之间有约 3–7% 的整体漂移。** 比较两个配置必须在同一时段交替运行，不能拿两天的数字相减。
4. **显卡被别的程序占着**（游戏、ComfyUI 已加载的模型）会缩小专家缓存。看 `engine.log` 里的 `expert cache N slots`。
5. **社区榜的综合分按 token 加权**，结构化题占约四分之三的输出。估计聊天速度看"对话"一列。
6. **换模型后第一条请求慢**，自适应层要把常用专家重新换进显存。

## 接入客户端与前缀缓存

- 接口是 OpenAI 兼容的 `<text_url>/v1`，另有 `/v1/messages` 和 `/v1/responses`；本地无 key，客户端里随便填。
- 引擎每读入 16,384 个新 token 留一个检查点，另在系统提示末尾和最后一轮各留一个。**把稳定内容（系统提示、工具定义、项目资料）放前面，新内容追加在后面。** 重写前缀（比如 agent 压缩上下文）会触发整段冷读：32K 上下文末尾追加新问题时，首字从 13.1 秒降到 6.7 秒。
- `GET <text_url>/health` 看模型是否加载；`GET <text_url>/v1/status` 的 `last_timings` 给出读入与生成速度、草稿提议数和采纳数。
- 机器上可能残留旧服务占着别的端口、配置不同，别和现用的混淆，见 [pitfalls.md](pitfalls.md)。

## 启动一启动就退出

日志为空、退出码 `0xC0000135`，是缺 CUDA 运行库的 DLL（如 `cublas64_13.dll`）。把 CUDA 13 的运行库放在你自己的固定目录里，启动前把它加进 `PATH`。详见 [pitfalls.md](pitfalls.md)。
